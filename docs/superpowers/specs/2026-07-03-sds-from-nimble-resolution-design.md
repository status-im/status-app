# nim-sds from nimble resolution — kill the checkout improvisations

**Date:** 2026-07-03
**Parent:** `docs/superpowers/prds/2026-07-03-statusgo-nimble-package-prd.md` (status-im/status-desktop#19907)
**Status:** approved design, pending implementation (issues 0005, 0006)

## Problem

statusgo's build tasks (statusgo.nims) consume nim-sds twice: as Nim modules
(resolved by nimble — correct) and as the source tree that produces the
`libsds` C archive linked by Go. For the second role they improvise: an env
override (`NIM_SDS_SOURCE_DIR`), else a sibling `../nim-sds` checkout, else a
git clone at the pin. The build can therefore compile sources that nimble
never resolved — a second source-of-truth for the same dependency, exactly
the class of drift the parent PRD exists to remove.

## Decision

**One rule: every sds build task builds the nimble-resolved nim-sds copy.**
Cross-compilation stays env/task-driven (the PRD's standing decision).
Per-target artifact packages via `?subdir=` become the upstream distribution
veneer on top of the same engine.

- Sibling convention, git cloning, and `NIM_SDS_SOURCE_DIR` are deleted from
  statusgo.nims.
- A patched/local sds is substituted the nimble-native way:
  `nimble develop --add:<path>` — the resolved copy then *is* that checkout.
  (This is already the PRD's plan for the app graph.)
- Flag-forwarded cross-install (`nimble install --os:… --cpu:…`) is
  **structurally unsupported** by nimble and stays out of scope; an upstream
  nimble issue is filed instead (see spike record 2).

## Design

### Engine (issue 0005 — statusgo.nims, no upstream dependency)

1. **Locate:** the sds source path comes from the same resolution the
   compile paths come from — `nimble.paths` (generated by `nimble setup`;
   in install context by the nested setup introduced in issue 0002). The
   `/pkgs2/sds-…` entry (store copy) or the develop-linked checkout path.
2. **Prepare:**
   - Develop-linked checkout (path outside the store): build **in place** —
     it is the developer's writable working copy; artifact locations stay
     exactly as today (`<checkout>/build`), so desktop's Makefile
     expectations are untouched.
   - Store copy (path under `/pkgs2/`): **copy to a scratch dir**
     (`.sds-build/` at the statusgo package root — dot-dir, never installed)
     and build there. The shared store stays pristine.
3. **Build:** unchanged — run sds's own tasks (`sds.nims` symlink trick)
   with `NIMFLAGS` carrying the exact `--path` set from `nimble.paths`
   (minus the sds store entry; the prepared copy is authoritative).
   All flavors go through this: host static (auto-link/install), desktop
   shared, iOS, Android.
4. **Delete:** `sdsSourceDir()` env/sibling/clone logic, `ensureSdsSource`'s
   git clone, `sdsPin()` (the pin lives in the manifest and is enforced by
   resolution itself — no hand-parsing).

Error mode: if `nimble.paths` has no sds entry, fail with an actionable
message ("run `nimble setup`" / "develop-link your sds checkout").

### Distribution veneer (issue 0006 — upstream nim-sds, gated)

nim-sds gains `targets/<flavor>/` subdir artifact packages (host-static,
ios, android-arm64, …). Each is a thin manifest:

- `requires` nim-sds at its own release version (tag-matched pins),
- a `before install` hook that materializes exact dep paths (nested
  `nimble setup`), copies the resolved sds to scratch, runs the sds task for
  its baked-in target (NDK/SDK from env, as today), and
- `installDirs = @["build"]` (+ `libsds.h` via installFiles) so the artifact
  lands in the store.

Result: `nimble install "…nim-sds?subdir=targets/ios@#v0.4.x"` is one-command
cross-target provisioning; targets coexist in the store because each subdir
is its own package identity. statusgo's make matrix does NOT depend on this —
it keeps the direct engine path (develop-linked and uncommitted-patch flows
must work).

Gates: the pending nim-sds patch queue merges; nim-sds tags releases (the
requires/tag pairing depends on it); upstream accepts the targets/ layout.

### sds build unification (part of the 0006 upstream work)

nim-sds's per-target tasks each hardcode their flag set — that duplication
collapses into **one parametric build entry point**: flag selection moves
into nim config keyed by `--os`/`--cpu`/defines (`when defined(ios)` etc.),
so every flavor is "one entry point + target flags" and the per-target tasks
shrink to one-line aliases. What canNOT become flags (verified limits):

- nimble has no library-artifact concept — `bin` builds programs, so
  nimble's native install build can never produce libsds by itself;
- the localized static flavors are a multi-command pipeline
  (`--compileOnly` → clang hidden-visibility → `ld -r -exported_symbol`
  → `ar`) — no flag combination expresses a post-link localization step, so
  a thin driver (task alias / 0006 install hook) survives to run it;
- flag-keyed install-time dispatch stays impossible (hooks never see
  `--os`/`--cpu`; spike record 2), and repeat same-version installs are
  silently skipped as satisfied, not overwritten — env-keyed dispatch
  (`SDS_TARGET=…`) is hook-visible but leaks into dependency-driven
  installs, rejected.

Result: 0005's engine and 0006's subdir hooks call the one entry point with
target flags instead of dispatching across task names.

## Spike record 1 — subdir packages (nimble 0.22.3, all local)

Toy multi-target repo served over localhost (dumb HTTP; `git://` gets
rewritten to https, dumb HTTP can't serve nimble's shallow clone — pinned
revs force a full clone and work).

- `url?subdir=<path>@#<rev>` parses, pins, installs. Rev must follow the
  subdir (`@#rev?subdir=` is rejected).
- Subdir packages get **name-keyed store entries** — two targets of one
  repo/rev coexist. Target-in-identity dissolves the store-collision blocker.
- Bin-less artifact packages: only install hooks fire (no build phase).
  `before install` runs in a buildtemp staging dir and its outputs ARE
  carried into the store by `installDirs`. `after install` runs in the final
  store dir.
- **The staging dir contains only the subdir's own files.** The parent repo
  is never present (`../..` is the store's internals); the clone sits in
  nimble's pkgcache at an unknowable path. `paths = @["../../…"]` does not
  change staging or store contents (it only adds consumer compile paths —
  and silently breaks for URL installs generally).
- Consequence: a subdir target package cannot build from repo-root sources;
  it must `requires` its own repo's main package and build from the
  resolved copy — i.e. the engine.

## Spike record 2 — hook flag visibility (0.22.3 and master 0.99.1)

Probe package with instrumented before/after install/build hooks + a bin
printing its compile target, installed plain and with `--os:linux
--cpu:arm64`:

- Hooks see host values only: `hostOS`/`hostCPU` unchanged, no target in
  `paramStr` (full nims-eval command captured) or env, on both versions.
- The **bin compile does receive the target** (nim invoked
  `aarch64-linux-gnu-gcc`), and on master **custom tasks** get forwarded
  compilation flags — consistent with keeping cross-compilation task-driven.
- The store is target-blind on both: same `name-version-checksum` dir; with
  a host copy installed, a `--os:linux` install of the same package no-ops.
- Source (master): `execNimscript` forwards `getCompilationFlags()` only for
  custom tasks, and the flag accessor is not defined for the install action;
  `getCacheDir = name-version-checksum`. Both blockers are structural.
- → Upstream nimble ask (to file): forward target flags to hook evaluation
  AND target-qualify the store dir; that would eventually allow
  `nimble install pkg --os:… --cpu:…` to supersede subdir target packages.

Operational gotchas recorded during spikes: run `nimble install <url>` from a
neutral directory (inside a package dir, vNext also builds THAT package);
`file://` URLs bypass subdir parsing (local-path code path); nimble clones
into `~/.nimble/pkgcache` regardless of `NIMBLE_DIR`.

## Out of scope

- Changing which sds flavors exist or their recipes (sds.nimble owns them).
- The nim-sds version bump / protocol decision (messaging team).
- Prebuilt-binary hosting.

## Testing

(develop-linked path), plus a negative: unset develop-link + empty store →
